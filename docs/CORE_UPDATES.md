# 核心更新

MiroFish 的推演核心（`backend/`、`locales/` 和构建好的界面）可以在软件内单独更新，不必重新下载安装包。本文说明它能做什么、不能做什么、为什么可信，以及维护者发布更新的步骤。

## 能更新什么

| 能通过核心更新 | 必须发新的安装包 |
| --- | --- |
| `backend/app`、`backend/scripts` 中的推演、图谱、报告逻辑 | Studio 层（`local_studio/`）、桌面壳、托盘、备份恢复 |
| `locales/` 多语言文案 | Python 运行时、第三方依赖（`uv.lock` 中的任何变化） |
| 与核心配套的前端界面 | 安装器、图标、安装目录结构 |

核心更新包会声明自己需要的 Studio 接口级别、Python 版本以及**完整的依赖集合**。只要其中任何一项与已安装的运行环境不一致，工作台会拒绝安装，并提示需要新的完整安装包。这是有意的：核心更新只换代码，不改运行环境，所以不会把软件带进"代码和依赖对不上"的状态。

## 上游 MiroFish 与更新包的关系

更新包**不是**上游源码的直接拷贝。本仓库在上游代码上做了本地改动（逐文件清单见 [UPSTREAM_DELTA.md](./UPSTREAM_DELTA.md)），所以每个更新包都由本仓库的发布流程合并上游变化、跑完整测试后构建。上游自己的新版本需要先合并进本仓库，再发布为核心更新；`source_info.json` 记录采用的上游提交，更新包的清单里也带有这一信息，界面会显示"来自上游提交"。

## 它为什么可信

下载并执行代码是高风险操作，所以有多层限制：

1. **签名**：每个更新包带 `MANIFEST.json`（逐文件列出大小与 SHA-256）和它的 Ed25519 签名。程序内置发布者公钥；签名不通过，不会解压、不会运行。即使下载地址被劫持，也无法让软件运行未经签名的代码。
2. **只允许这几个位置**：更新只能写入 `backend/`、`locales/`、`frontend/dist/` 和 `source_info.json`。清单之外的内容、路径逃逸（`..`、绝对路径、盘符）、链接文件、加密条目、重复或大小写别名文件、Windows 保留名，一律拒绝。
3. **启动前再校验**：已安装的核心每次启动引擎前都会重新校验签名与全部文件哈希。被改动、缺文件、多文件，都会回退到安装包自带的核心，并在界面提示原因。
4. **只升不降**：更新必须高于安装包自带的核心版本；之后安装了更新的完整安装包，旧的核心更新会自动失效。
5. **自动回退**：切换前先备份记录；切换后引擎没有正常启动，会自动恢复到原来的版本。任务进行中不允许切换。
6. **下载地址限制**：只信任 `github.com` 及其下载域名（HTTPS）；重定向到其他地址会中止。

**边界**：信任根是签名私钥。持有私钥的人可以让所有安装了该公钥的软件运行其代码，所以私钥务必妥善保管（见下）。签名也无法保护已经被攻破的电脑。

## 第一次启用（维护者，只需一次）

核心更新在**没有公钥时是关闭的**：`local_studio/core_update.py` 中的 `UPDATE_PUBLIC_KEY_HEX` 默认为空，此时工作台不会安装、也不会使用任何核心更新。

1. 在离线、可信的电脑上生成密钥对：

   ```powershell
   python scripts/core-keygen.py
   ```

   输出包含 `public_key` 和 `private_seed`。私钥只显示这一次。

2. 把 `private_seed` 保存为仓库的 Secret `CORE_SIGNING_KEY`（Settings → Secrets and variables → Actions），并在另外至少一处安全保管。不要提交到仓库、不要贴到 Issue。

3. 把 `public_key` 填进 `local_studio/core_update.py` 的 `UPDATE_PUBLIC_KEY_HEX`，发布一个新的完整安装包。之后用该安装包的用户即可使用核心更新。

私钥丢失或泄露时：生成新密钥对、更新 Secret 和公钥并发布新的安装包。旧安装包无法信任新密钥，需要用户重新安装。

## 发布一个核心更新

```bash
git tag -a core-v1.1.1 -m "修复推演中断后的状态显示
新增成本预估"
git push origin core-v1.1.1
```

`core-release.yml` 会测试、构建界面、签名并发布名为 `mirofish-core-1.1.1.zip` 的 Release 附件（不会成为仓库的 "latest"）。标签注解会显示为界面里的更新说明。版本号必须是 `主.次.修订`，且高于安装包自带的核心版本（`source_info.json` 的 `core_version`）。

本地试构建（需要先 `npm --prefix frontend run build`）：

```powershell
$env:CORE_SIGNING_KEY = "<64 位十六进制私钥>"
python scripts/build-core-bundle.py --version 1.1.1 --out dist-core
```

构建脚本会在生成后用与软件相同的代码把更新包装进一个临时目录；会被软件拒绝的包，在这里就会失败。

### 什么时候要改 `STUDIO_API_LEVEL`

`STUDIO_API_LEVEL`（`core_update.py`）描述"核心的界面与后端"和"启动它的 Studio 层"之间的约定：`/studio-api` 接口以及引擎的启动方式。如果你做了会让旧核心无法工作的 Studio 层改动，就提高它；更新包声明的支持范围不包含当前级别时，工作台会拒绝安装。

## 用户怎么用

- **工作台 → 核心版本**：查看正在使用的核心、检查更新、一键下载并启用。
- 无法访问 GitHub 时，可以在同一页面「导入更新包」，选择从官方渠道取得的 `mirofish-core-*.zip`，校验规则与在线更新完全相同。
- 「回退到上一个版本」可随时回到之前的核心，直至安装包自带的核心。
- 已安装的核心保存在数据目录的 `core/` 下（Full 版为 `%APPDATA%\mirofish-studio-desktop\data\core`），重装软件不会丢失；最多保留当前版本和最近两个历史版本。

## 如果出问题

| 现象 | 说明 |
| --- | --- |
| 「此版本尚未启用核心更新」 | 该安装包未内置公钥，见"第一次启用" |
| 「更新包签名无效」 | 更新包不是官方签名的，或在传输中损坏；请只从官方发布页获取 |
| 「需要不同的 Python 依赖 / 更新版本的工作台」 | 此更新需要新的完整安装包 |
| 界面提示「已安装的核心更新未通过校验，正在使用内置核心」 | 已安装的核心被改动或损坏；会自动使用安装包自带的核心，可重新导入或下载 |
| 切换后提示「已自动恢复到原来的版本」 | 新核心没有正常启动；记录已在切换前备份（`records-pre-update-*.zip`） |
